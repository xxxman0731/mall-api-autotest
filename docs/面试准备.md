# 面试准备:高频追问与答题思路

围绕本项目的 15 个高频面试追问,附答题要点。建议先自己按要点复述三遍,再对照文档查漏补缺。

## 1. 介绍一下这个项目

要点:一句话定位(电商核心链路接口自动化测试框架)-> 被测对象(注册/登录/商品/下单)-> 你的职责(用例设计、框架搭建、落库校验、报告、CI)-> 量化成果(45+ 用例、失败自动归档、回归从人工分钟级到自动化秒级)。

## 2. 为什么选择数据驱动,数据驱动怎么实现的?

要点:用例与数据分离,新增用例不改代码、降低维护成本;实现上把请求参数与预期结果放在 YAML,pytest 的 parametrize 逐条加载执行;缺点是数据结构固定后灵活度受限,复杂场景用代码用例补充(如越权、库存不足)。

## 3. 你的框架分几层,每层职责是什么?

要点:配置层(config.yaml)、公共组件层(common:请求封装、DB 封装、日志、断言)、数据层(testdata/*.yaml)、用例层(testcases)、装配层(conftest fixture)。分层的好处:改环境不动用例、改断言不动数据。

## 4. token 怎么管理?怎么处理登录态?

要点:会话级 fixture 自动注册并登录主账号,登录接口返回 token;请求封装层支持 set_token,自动拼 Bearer 头;用例通过 auth_headers fixture 直接复用;无 token、无效 token 场景单独用数据用例覆盖。

## 5. 接口测试为什么要查数据库?

要点:接口返回成功不等于数据正确落库;举例:下单成功但库存扣减数量错误、金额计算错误、订单号重复,这些都是只断言响应发现不了的;所以注册后查 users 表(密码加盐 MD5)、下单后查 orders 表与库存。

## 6. 怎么设计断言,断言太弱/太强有什么问题?

要点:分层断言:状态码 -> 业务码 -> 关键字段 -> 数据库一致性;太弱容易漏问题,太强(比如断言整段响应)会因无关字段变化导致用例脆弱、维护成本高;断言只锁定与业务相关的关键字段。

## 7. 失败用例怎么定位?

要点:三层保障:请求/响应全程落日志;失败用例通过 pytest hook 自动归档异常信息到 logs/failures/;Allure 报告按用例展示失败堆栈。拿到日志先看状态码和业务码,再看落库结果,基本能定位到接口层还是数据层问题。

## 8. 冒烟测试和回归测试怎么区分,怎么落地?

要点:冒烟只测核心链路是否通(健康检查、登录、浏览、下单一条龙),发布/部署后先跑,快速反馈;全量回归覆盖所有用例,定时跑(每天凌晨)或提测触发;实现上用 pytest marker(smoke / regression)区分,Jenkins 分阶段执行。

## 9. 测试数据怎么准备和清理?

要点:每个测试会话开始前自动清理测试数据并重置库存,保证用例可重复执行;数据来源:YAML 静态数据 + 用例运行时动态构造(如库存不足场景临时插入库存为 1 的商品);避免用例之间数据耦合。

## 10. 如果一个用例失败了,可能是哪些原因?

要点:环境问题(服务没起、端口占用、依赖版本)-> 测试数据问题(脏数据、前置状态不满足)-> 断言过严(响应字段变化)-> 真实缺陷(逻辑错误、边界未处理)。排查顺序:先看日志确认环境与数据,再看失败堆栈,最后才是缺陷。

## 11. 压测是怎么做的?关注什么指标?

要点:工具选型(JMeter 做固定并发压测,Locust 做灵活脚本压测);流程:压测方案(并发 50、预热 5 秒、循环 10 轮)-> 造数据 -> 压测 -> 分析;关注 TPS、响应时间(平均/90/99 分位)、错误率、服务器 CPU/内存;瓶颈定位:慢 SQL、无索引、连接池不足。

## 12. 说说你定位"慢 SQL"的过程

要点:压测发现下单接口响应时间随并发上升明显 -> 用 EXPLAIN QUERY PLAN 看执行计划,发现按 user_id 查订单走全表扫描 -> 添加索引 -> 执行计划变为 SEARCH,响应时间明显下降 -> 总结:先看指标,再定位到 SQL,用执行计划验证,优化后回归验证。

## 13. 自动化覆盖率达到多少?你怎么看待覆盖率?

要点:核心链路接口覆盖 100%,边界/异常场景覆盖主要分支;覆盖率是手段不是目标,漏测的往往不是代码行而是业务场景;用例质量(断言有效性、稳定性)比数量重要。

## 14. 这个框架还有哪些可以改进的地方?

要点:增加环境隔离(测试/预发多环境切换);断言封装成 JSONPath/Schema 校验;失败自动重跑与并发执行(pytest-xdist);接入钉钉/企业微信失败告警;把 token 过期、并发下单等场景纳入;接入覆盖率统计。

## 15. 测试左移/右移你在这个项目里有体现吗?

要点:左移:接口文档评审阶段就设计用例,把需求规则(用户名长度、下单数量限制)转化为边界用例;右移:CI 定时回归 + 失败告警 + 线上监控,形成持续质量反馈;可以用这个框架说明"质量保障不只在中期的执行阶段"。
